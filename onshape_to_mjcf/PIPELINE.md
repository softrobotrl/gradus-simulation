# Segmented leg → MuJoCo MJCF pipeline

End-to-end, reproducible export of the Onshape leg prototype to a merged MuJoCo
model: **Onshape assembly → `onshape-to-robot` → tendon/spring merge → `leg.xml`**.

Station order, link lengths, hole positions/angles and tendon routing are read
from Onshape. The bore/cable-hole and tendon-ring radii are configurable in
`config.json`.

---

## Quick start

```bash
# from the repo root
cp .env.example .env        # fill in ONSHAPE_API / ONSHAPE_ACCESS_KEY / ONSHAPE_SECRET_KEY
python -m onshape_to_mjcf.build
```

No Onshape API key? Use the model zip pinned in the **#reinforcement-learning**
Discord channel.

Output:

```
urdf/gradus/sim/
├── leg.xml        merged model
├── scene.xml      leg.xml + floor/light
└── assets/        STL meshes
```

`onshape_to_mjcf.render` additionally writes `leg_pose_*.png` into the same
directory.

Open the interactive viewer:

```bash
DISPLAY=:0 python -m mujoco.viewer --mjcf urdf/gradus/sim/scene.xml
```

Headless render:

```bash
xvfb-run -a env MUJOCO_GL=glfw python -m onshape_to_mjcf.render \
    --xml urdf/gradus/sim/scene.xml --out urdf/gradus/sim
```

## Why a clean `Leg-Sim`

The original assembly cannot be exported by `onshape-to-robot`:

- Its 14 stations are generated by two assembly **linear patterns**;
  `onshape-to-robot` does not expand patterns.
- Its joints are **Cylindrical + Planar** surrogate mates, not `dof_*`.
  `onshape-to-robot` only turns `dof_*` mates into joints.
- Without `dof_*` it writes every instance as an independent free body at the
  origin.

`onshape_to_mjcf/assembly.py` builds a clean assembly with:

- 28 explicit half-disk instances (the two printed halves of each station),
- one **mate group** per station (merges the halves),
- 13 **BALL** mates named `dof_00` … `dof_12` between consecutive stations.

`onshape-to-robot` then produces a proper 14-link tree with 13 ball joints.

## Pipeline

```
onshape_to_mjcf/config.json          IDs, bore/hole/ring radii, material defaults
        │
        ▼
onshape_to_mjcf/assembly.py    ensure/reuse Leg-Sim  (--rebuild to recreate)
        │
        ▼
onshape-to-robot             leg_base.xml + assets/   (temp dir, deleted)
        │
        ▼
onshape_to_mjcf/merge.py            sites + tendons + motors + rod spring + mass
        │
        ▼
urdf/gradus/sim/leg.xml      validated (loads, 300 steps, no NaN)
```

```

```

- **Inner** (r = 16 mm): 14 sites each, hip → foot. Actuates all 13 joints.

## How the tendons are actuated

Each tendon is a MuJoCo **`<spatial>`** tendon: an ordered list of `<site>`
elements. MuJoCo computes its length from the site positions:

```
L(q) = Σ |p_{i+1}(q) − p_i(q)|
```

and internally the Jacobian `J = ∂L/∂q`.

The default model is **servo-driven**: one `<position>` actuator per tendon,
controlling the tendon length.

```xml
<position name="servo_tendon_inner_front"
          tendon="tendon_inner_front"
          kp="5000" kv="50"
          ctrlrange="0.5611 0.5925"
          forcerange="-200 0"/>
```

- `ctrl` = **target tendon length** (m), not force.
- A servo command is an angle: `ctrl = L0 − r_spool · θ`.
- `ctrlrange` = `[L0 − stroke, L0]` = **stroke limit**
  (`stroke = r_spool · θ_max`).
- `forcerange` = `[−F_max, 0]` = **torque limit**, tension-only
  (`F_max = τ_servo / r_spool`).
- `kp` / `kv` = servo position/velocity gains.
- The force is `f ≈ kp·(ctrl − L) − kv·L̇`, clamped by `forcerange`, then
  distributed over the joints by `τ = Jᵀ·f`.

Mapping from a real servo:

| servo spec | model |
|---|---|
| stall torque `τ` | `F_max = τ / r_spool` |
| travel `θ_max` | `stroke = r_spool · θ_max` |
| no-load speed `ω_max` | rate-limit `ctrl` (not in the XML) |
| spool radius | `r_spool` |

Placeholders in `onshape_to_mjcf/config.json`: `2 N·m`, `r = 10 mm`, `180°` →
`F_max = 200 N`, `stroke = 31.4 mm`.

### Important: initialise `data.ctrl`

For a position servo, `data.ctrl = 0` is **not "no pull"** — 0 is below the
`ctrlrange` and clamps to **maximum pull**. With the default gains that is
`kp · stroke = 5000 × 0.0314 ≈ 157 N` per tendon, not a measured hardware
pretension; it is simply the servo force at full stroke command. At reset, set
every servo to its rest length:

```python
data.ctrl[:] = model.actuator_ctrlrange[:, 1]   # L0 for all tendons
```

Then command a pull by moving one target shorter:

```python
i = model.actuator("servo_tendon_inner_front").id
lo, hi = model.actuator_ctrlrange[i]
data.ctrl[i] = hi - 0.5 * (hi - lo)             # half stroke
```

### Verified servo actuation (2 N·m, 10 mm spool, 31.4 mm stroke)

| command | force | tip |
|---|---|---|
| rest | 0 N | +16 mm X |
| 25 % stroke | −35 N | +29 mm X |
| 50 % stroke | −71 N | +43 mm X |
| 100 % stroke | −142 N | +69 mm X |
| blocked at 100 % | −200 N (stall) | — |

### Force-motor alternative

`--motors` produces the force-controlled variant instead:

```xml
<motor name="act_tendon_inner_front" tendon="tendon_inner_front"
       ctrlrange="0 2000" gear="-1"/>
```

Here `ctrl` is newtons, `gear=-1` makes positive ctrl a pull (tension-only),
and `data.ctrl[i] = 0` really is zero force.

### Not modeled

- **Speed limit**: `kv` damps, but there is no hard `ω_max`. Rate-limit the
  target in your controller
  (`ctrl += clamp(target − ctrl, ±r·ω_max·dt)`) or use a smaller timestep.
- **Torque–speed curve**: `forcerange` is constant. A real servo reaches stall
  torque only near zero speed. For a closer match, scale `F_max` by
  `max(0, 1 − |L̇| / (r·ω_max))` in a custom controller.

The spatial tendons themselves are **inextensible kinematic paths** (no
`stiffness`/`springlength`). Compliance comes from the rod (joint stiffness)
and the servo/actuator.

## Tuning

| Parameter | Effect |
|---|---|
| `--bore-radius` | backbone bore radius used to locate holes (m) |
| `--hole-radius` | cable hole radius to detect (m) |
| `--inner-radius` / `--outer-radius` | tendon-ring radii from the bore centre (m) |
| `--rod-d` | backbone diameter (m); `k ∝ d⁴` |
| `--rod-E` | backbone Young's modulus (Pa); `k ∝ E` |
| `--density` | PLA density (kg/m³) |
| `--servo` | position-servo model (default; `use_servos` in config) |
| `--motors` | force-motor model instead |
| `--servo-torque` | servo stall torque (N·m) |
| `--spool-radius` | tendon spool radius (m) |
| `--servo-travel` | max spool travel (rad) |
| `--servo-kp` / `--servo-kv` | servo position / velocity gains |
| `--tendon-fmax` | motor force limit (only with `--motors`) |
| `--free-base` | keep a floating root instead of a fixed base |
| `--no-rotate` | leave the CAD's 45° hole orientation |

`onshape_to_mjcf/config.json` holds the defaults (including the hole/ring match
tolerances); CLI flags override them. After a CAD change, run with `--rebuild`
so the `Leg-Sim` assembly is regenerated from the current model.

## Limitations / notes

- **Ball joint stiffness is isotropic**: bend and twist share the same
  `128 N·m/rad`. For a pultruded rod, twist is softer (`GJ/EI` ≈ 0.3–0.8).
  Splitting into three hinges (bend X, bend Y, twist Z) is possible if needed.
- The rod is not simulated as a deformable body; it is the equivalent joint
  spring.
- The model is a lumped 14-link approximation of a continuous rod.
- Tendon paths are straight chords between holes (no pulley wrapping).
- Screws and the physical backbone are omitted; the backbone is replaced by
  the joint springs.
- The API key returns **403** on element delete, so `--rebuild` creates a new
  `Leg-Sim` tab; delete old ones in the Onshape UI.
- `onshape-to-robot` reports “no dynamics” because the Onshape parts have no
  material; `merge.py` replaces the `1e-9 kg` inertials with mesh-derived
  mass. **Mass assumes solid parts (100 % infill)**; printed parts with a
  lower infill will be lighter than the model.
